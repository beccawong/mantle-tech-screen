❯ the worker tasks aren't stored anywhere. asyncio only keeps weak references   
  to tasks, so a task with no reference can be garbage-collected. Also, if a    
  worker crashes, nothing notices. After the pending fix, that would turn into  
  a hang. what does this mean? what are weak references? are you implying these 
  tasks can be garbage-collected too early?                                     

⏺ Yes, that's what I was implying, and I overstated it. In this script the tasks
  won't realistically be garbage-collected early. The crash half of the point
  is real, though I worded it loosely. Here are both.

  What a weak reference is

  Python frees an object once nothing refers to it anymore. A normal ("strong")
  reference keeps the object alive:

  x = SomeObject()   # x holds a strong reference, so the object stays alive

  A weak reference lets you point at an object without keeping it alive. If the
  weak references are the only ones left, Python can collect the object. A
  WeakSet is a set made of weak references. Caches and registries use it when
  they want to track objects without stopping them from being freed.

  Why it matters for asyncio tasks

  asyncio.create_task() registers the new task in the event loop's WeakSet of
  all tasks. The Python docs
  (https://docs.python.org/3/library/asyncio-task.html#asyncio.create_task) warn
  about this directly:

  ▎ Save a reference to the result of this function, to avoid a task 
  ▎ disappearing mid-execution. The event loop only keeps weak references to 
  ▎ tasks.

  In hn.py:177, the result is thrown away:

  for _ in range(DEFAULT_WORKERS):
      asyncio.create_task(self.worker())   # return value discarded

  So the only reference you hold is gone, which is the pattern the docs warn
  against.

  Why it's unlikely to bite here (my correction)

  A task that is waiting on something is usually still reachable through what
  it's waiting on:

  - While a worker is in await asyncio.sleep(0.01), the loop holds a timer, the
    timer holds a future, and the future holds a callback that wakes the task.
    That chain keeps the task alive.
  - While it's in await asyncio.to_thread(...), the thread pool holds the work
    item, which leads back to the task the same way.

  Collection only really happens when a task waits on a future that nothing else
  references. That's rare, and this code doesn't do it. So treat this as good 
  practice, not a live bug. In an interview I'd mention it in one line ("I'd
  keep references to these tasks, per the docs") and wouldn't rank it next to
  the pending race.

  The crash part, stated more precisely

  This is the part that matters. If a worker raises an exception, the exception
  is stored on the task object. Nobody ever awaits the task, so nobody sees it.
  You'd at most get a "Task exception was never retrieved" warning at shutdown.
  The worker is simply dead, with no error shown.

  What could raise? For example, clean_text(item["text"]) when text isn't a
  string, or an item with no "id" key.

  What happens next depends on the code:

  - Current code: pending was already decremented when the job was popped. A
    crash silently loses that item's whole reply subtree, and the crawl carries
    on with one fewer worker. If all 8 workers die while jobs are still queued,
    pending never reaches 0 and wait_until_done loops forever. So a hang is
    possible even today.
  - After the pending fix:
    - If the decrement goes at the end of the loop body without finally, a
      single crash leaves pending stuck above 0, and the crawl hangs. That's the
      case I meant earlier.
    - If it goes in a finally, as I suggested, the count stays correct. But
      crashed workers are still dead, so the all-workers-die hang remains.

  The robust fix for both

  Keep the tasks and await them, so their exceptions surface:

  workers = [asyncio.create_task(self.worker()) for _ in range(self.workers)]
  await self.wait_until_done()
  self.stopped = True
  await asyncio.gather(*workers)   # re-raises any worker exception

  Even better: catch errors per item inside worker(), log them and move on, so
  one bad comment can't kill a worker. An asyncio.Queue with queue.join() /
  task_done() would also replace the hand-rolled pending counter and the polling
  loop. That idiom is designed for exactly this, and it removes the race.

❯ Is create_task how you put something into event loop? I only used to          
  asyncio.run(main) for example and the async/await syntax                      

⏺ Yes. create_task is the main way to start something running concurrently on
  the event loop. If you've only used asyncio.run and await, you may not have
  needed it, because those already handle tasks for you.

  The three pieces

  asyncio.run(main()) creates an event loop, wraps main() in a task, runs it
  until it finishes, then shuts the loop down. Every async program has to start
  somewhere, and this is the usual entry point.

  await some_coroutine() does not create a new task. It runs the coroutine
  inside the current task, and the current task waits there until the coroutine
  finishes. While it waits (on a sleep, a network call, and so on), the loop is
  free to run other tasks, but await alone never creates them.

  asyncio.create_task(some_coroutine()) wraps the coroutine in a new task and
  schedules it on the loop. It returns right away, without waiting. The task
  starts running the next time the current code reaches an await and hands
  control back to the loop.

  Seeing the difference

  import asyncio, time

  async def job(name):
      await asyncio.sleep(1)
      print(name, "done")

  async def sequential():
      await job("a")        # wait 1s
      await job("b")        # then another 1s
                            # total: ~2s

  async def concurrent():
      t1 = asyncio.create_task(job("a"))   # starts, returns immediately
      t2 = asyncio.create_task(job("b"))   # starts, returns immediately
      await t1              # both sleep at the same time
      await t2              # total: ~1s

  for f in (sequential, concurrent):
      start = time.monotonic()
      asyncio.run(f())
      print(f.__name__, round(time.monotonic() - start, 1), "s")

  With only await, your async code still runs one step at a time. It only
  overlaps with work that's already running somewhere else. create_task is how
  you create that "somewhere else".

  The everyday shortcut: gather

  You may have seen this instead:

  await asyncio.gather(job("a"), job("b"))

  gather calls create_task on each coroutine for you and waits for all of them.
  Most code uses it rather than calling create_task by hand.

  How this maps to hn.py

  for _ in range(DEFAULT_WORKERS):
      asyncio.create_task(self.worker())   # start 8 workers, don't wait for 
  them
  await self.wait_until_done()             # main keeps going and polls the 
  counter

  This code needs create_task instead of gather because main has to keep doing
  something (polling pending) while the workers run. It also needs the workers
  to stop when it says so. But because it never awaits those tasks afterward,
  worker errors go unseen. That's why my suggested fix ends with await 
  asyncio.gather(*workers): it starts the tasks the same way, but still collects
  their results and exceptions at the end.

❯ what is asyncio.sleep? Is that the sleep needed for asyncio code?             

⏺ Yes. Inside async code, asyncio.sleep is the sleep you want. time.sleep would
  freeze everything.

  The difference

  time.sleep(1) blocks the whole thread for a second. The event loop runs on
  that thread, so every task stops: no other worker runs, no timers fire,
  nothing happens.

  await asyncio.sleep(1) pauses only the current task. Under the hood it tells
  the loop "wake me in 1 second" and hands control back. The loop runs other
  tasks in the meantime and resumes this one when the timer fires.

  import asyncio, time

  async def bad(name):
      time.sleep(1)            # blocks the loop
      print(name)

  async def good(name):
      await asyncio.sleep(1)   # gives control back to the loop
      print(name)

  async def main():
      t = time.monotonic()
      await asyncio.gather(bad("a"), bad("b"), bad("c"))
      print("time.sleep:", round(time.monotonic() - t, 1), "s")    # ~3s, one 
  after another

      t = time.monotonic()
      await asyncio.gather(good("a"), good("b"), good("c"))
      print("asyncio.sleep:", round(time.monotonic() - t, 1), "s") # ~1s, all at
  once

  asyncio.run(main())

  The general rule

  The event loop switches tasks only at an await. Any code that waits without
  await (time.sleep, requests.get, a slow file read, heavy computation) freezes
  all tasks until it finishes.

  That's why hn.py wraps its HTTP calls like this:

  await asyncio.to_thread(get_json, f"item/{item_id}")

  http.client is blocking, like time.sleep. to_thread runs it on a separate
  thread so the loop isn't stuck while it waits. (The usual alternative is an
  async HTTP library like aiohttp or httpx.)

  A trick: await asyncio.sleep(0)

  Sleeping for zero seconds still hands control back to the loop. It means "let
  other tasks run, then come back to me." It's useful in long loops that
  otherwise never await.

  Where hn.py uses it

  tasks keep waking up just to check whether anything changed. An asyncio.Queue
  removes them. A worker that calls await queue.get() sleeps until a job
  actually arrives, and await queue.join() wakes up exactly when the last job is
  marked done. That's the same rewrite that fixes the pending race.
